# Публичный Quorum и постоянная история

Локальный режим сохраняет существующую SQLite и MCP stdio без изменения старых записей. Для публичного сервера задайте точный HTTPS `QUORUM_PUBLIC_ORIGIN` и `QUORUM_USERS`. Без явно настроенных пользователей публичный режим не запускается. Секреты и конфигурацию окружения храните вне Git.

Оператор создаёт отдельный случайный ключ для каждого пользователя:

```bash
python -m app.accounts first-user
```

Команда выводит имя, секретный `access_key` и фрагмент `configuration` с SHA-256-хешем. Передайте пользователю ключ приватно, а объект configuration добавьте в JSON `QUORUM_USERS`. Для нескольких пользователей объедините объекты по именам. Обычный пароль вместо случайного ключа не используйте. Сервер хранит в окружении только хеш ключа. Повторная выдача выполняется заменой хеша соответствующего пользователя и развёртыванием конфигурации.

Браузер запрашивает имя и ключ через HTTP Basic; API использует ту же авторизацию. Доступ разрешён только через HTTPS-прокси. Изменяющие запросы передают точный `Origin`, совпадающий с `QUORUM_PUBLIC_ORIGIN`. `/api/health` доступен без ключа для проверки готовности. HTML, API, документация и файлы панели защищены; авторизованные ответы имеют `Cache-Control: no-store`.

## Хранилище и изоляция

Для публичного постоянного хранилища задайте `QUORUM_DATABASE_URL`. PostgreSQL-соединение с внешним хостом использует verify-full и системное хранилище доверенных CA. Каждый пользователь получает отдельную серверную схему, имя которой образуется из SHA-256 стабильного имени пользователя. Все отчёты, задачи, кэш и бюджеты находятся в этой схеме. Клиент не выбирает схему и не может запросить чужой отчёт по ID. Данные локального оператора не становятся общими публичными данными.

Альтернатива для одного узла — `QUORUM_DATABASE_PATH` на постоянном диске: пользователи получают отдельные файлы под каталогом accounts. Каталог должен быть приватным и сохраняться при обновлениях. Простое указание пути на временном диске не делает данные постоянными. Для нескольких серверов используйте PostgreSQL.

Глобальный `GITHUB_TOKEN` локального оператора не передаётся публичным пользователям. По умолчанию они анализируют открытые репозитории. При необходимости оператор задаёт индивидуальный `github_token` в записи нужного пользователя; чужие токены и кэш не разделяются.

## Лимиты GitHub

Проверенный ответ GitHub кэшируется на 60 секунд в постоянной БД пользователя. Повтор создаёт новый снимок истории без повторной загрузки; `metrics.collection.cache` показывает время исходного сбора и срок кэша. В одном процессе одновременно выполняется один сбор для пользователя. Общие PostgreSQL-бюджеты ограничивают новые сборы до 10 в минуту и изменяющие запросы до 60 в минуту на пользователя.

Ответ GitHub о rate limit сохраняет паузу из Retry-After или X-RateLimit-Reset. Пауза переживает перезапуск; API отвечает 429 с Retry-After и не повторяет запросы до её окончания. Необязательные недоступные выборки остаются явно помеченными в отчёте. Ограничения стороннего GitHub API и права токена сохраняют силу.

## Проверки

`tests/test_public_access.py` проверяет двух пользователей, отсутствие доступа к чужим ID и задачам, сохранность после перезапуска, раздельный кэш, отсутствие наследования приватного токена оператора, отказ без Origin и сохранение паузы GitHub. CI запускает тот же сценарий с отдельной PostgreSQL 17. Успешные локальные проверки не заменяют проверку размещённого сервера.

## Живое размещение — 11.11.2026

Сервер: https://memorim-quorum.onrender.com. Приложение работает на Render с отдельной PostgreSQL 17 в Neon (`calm-star-15166872`). TLS проверяет имя сервера и системные CA; Docker задаёт `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` для бинарного libpq. [CI](https://github.com/memorim/quorum-github-analyzer/actions/runs/43068441071) прошёл.

На реальном HTTPS-адресе проверены две отдельные технические учётные записи: HTML требует авторизацию, анонимный API получает 401, запись без Origin — 403. Первый пользователь создал два демонстрационных снимка и одну задачу; второй не видел ни отчётов, ни задачи, а обращение к чужому ID получило 404. Второй пользователь создал собственный снимок. После пересоздания сервера (deploy `dep-dbqai2jncjis738ussm0`) сохранились два отчёта и задача первого пользователя, один отчёт второго и изоляция по ID. Данные теста получены через явный demo endpoint; они не выдаются за результат живого сбора GitHub.

Живой запрос к GitHub получил 429 из-за квоты анонимных запросов с общего адреса Render. Сервер сохранил паузу в PostgreSQL и вернул положительный Retry-After; повтор не выполнял новый сбор. Положительный сценарий сбора и кэша проверен в CI с контролируемым ответом. Для реального сбора при исчерпанной общей квоте задайте собственный read-only `github_token` конкретному пользователю; внешняя квота GitHub не отменяется приложением.
